# Regions, regional prices and the demo-first trial

Built 10 October 2026 (R1 of `docs/RWANDA_LAUNCH_PLAN.md`, plus section 12's demo-first trial). Handover: `docs/handovers/r1-regions-trial.md`.

## Regions

Regions are data: the `PricingRegion` table (`key`, `name`, `currency`, `countries[]` as ISO codes, `paymentMethods[]` = `momo` | `card`, `active`, `sortOrder`), managed at **Admin → Regions and prices** and read through `lib/region.ts` (`getRegions()`, cached 30 s, seeds in `lib/region-format.ts` as the fallback).

| Key | Countries | Currency | Payment |
|---|---|---|---|
| `RW` | RW | RWF | Mobile Money (R4) and card (Paddle, charged in USD) |
| `EAC` | KE, UG, TZ, BI, SS, CD, SO | USD | Card |
| `GLOBAL` | everything else (no country list) | USD | Card |

A country belongs to exactly one active region; the region with no countries takes the rest and cannot be switched off.

**Which region someone is in**

- **Public pages** (`/pricing`): the visitor's real location, **no manual switch** (the "Not in Rwanda? See other prices" links are gone, and `?region=` / the `bp-region` cookie are ignored). `displayRegion()` resolves, first match wins: (1) the **"Use my location" result**, the signed `bp-geo` cookie (below); (2) the host's IP country: Cloudflare's `cf-ipcountry`, or on Netlify only the `x-nf-geo` header (base64 JSON, `country.code`; missing means the catch-all region) (`lib/platform/headers.ts`; each host only trusts its own headers, see `docs/DEPLOY_NETLIFY.md`, DNS); (3) outside production only, `ANALYTICS_DEV_COUNTRY`; (4) the catch-all region. `cf-ipcountry` always beats `ANALYTICS_DEV_COUNTRY`, so a tunnel through Cloudflare shows real detection. No third-party IP lookup is used.
- **"Use my location"** (small button on `/pricing`): the browser's `navigator.geolocation` (the visitor must allow it) → `POST /api/geo/country` `{lat, lng}` → the server validates the ranges, rate-limits per IP (`cf-connecting-ip`, on Netlify `x-nf-client-connection-ip`; missing = one shared bucket; 20 an hour, `RATE_LIMITS.geoCountry`), looks the country up through the provider adapter `lib/geo/provider.ts` (`GEO_PROVIDER`): **`builtin` (default, free, offline)** = a point-in-polygon lookup over the border data of the npm package `@rapideditor/country-coder` (ISC licence, about 690 KB, server-side only, no outside service, `lib/geo/builtin.ts`); **`google`** = the Google Geocoding API (`result_type=country`, `GOOGLE_MAPS_API_KEY`, server-side only, needs billing), kept for later. Built-in answers land points only (open sea gives no country) and its borders are generalised, so a point within a few hundred metres of a border may fall on the wrong side; fine for choosing a price list. Attribution: country-coder, Copyright (c) country-coder contributors, ISC (github.com/rapideditor/country-coder); its README says it uses public border data and Wikidata, so check its data licence again before redistributing the data separately and answers only `{enabled: true, country: "RW"}`; without a key it answers `{enabled: false}`. It sets `bp-geo` (httpOnly, 24 h, `<CC>.<issued-at>.<HMAC-SHA256>`, key derived from `ENCRYPTION_KEY`, `lib/geo-cookie.ts`) and the page refreshes. **Coordinates are never stored or logged.** No location shared → nothing changes.
  - **Availability (google provider only; builtin is always on and the button always shows):** `lib/geo-availability.ts` probes the Geocoding API (a fixed point, never a visitor's) and caches the answer ~10 minutes per instance. `REQUEST_DENIED` / quota errors (for example the Google project has no billing yet) hide the button on `/pricing` and make `/api/geo/country` answer `{enabled:false}`; visitors never see an error, and the denial is logged once. It comes back by itself within 10 minutes of Google working.
  - **The public price display can be changed by a determined visitor.** `POST /api/geo/country` accepts any coordinates inside the valid ranges (the browser's location is the visitor's to report, and dev tools or a script can send any point), so anyone can make `/pricing` show another region's prices for a day. That is accepted on purpose: it is display only. **Billing is protected elsewhere:** the company's prices come from `Business.pricingRegion` (the declared sign-up country), and the soft region check below flags a company whose IP country at sign-up or payment belongs to a dearer region, for admin review.
  - **Tradeoff:** a valid `bp-geo` beats `cf-ipcountry` even when they differ. That is the point (a visitor on a VPN gets the prices of where they really are), and it also means a visitor can pick a region by lying to the browser's location (dev tools can fake it). Accepted: pricing display is not a security boundary; **billing uses `Business.pricingRegion` (sign-up country), never this**. The cookie lasts 24 h, so "this session" is approximated by "the last day".
- **Local development override:** `REGION_OVERRIDE=1` (off by default, never set it in production) makes `?region=EAC` work again and `proxy.ts` keep it in the `bp-region` cookie. Without it, `proxy.ts` sets no cookie and the query and cookie are ignored. With it, the override beats the location and IP.
- **A company**: `Business.pricingRegion`, set **once** from the sign-up country (`regionKeyForCountryName`; every sign-up country has its ISO code in `COUNTRY_CODES`, so a region an admin adds for, say, Nigeria takes Nigerian sign-ups at once): at `ensureAccount` for email sign-ups, and on the **first** `/welcome` save for Google sign-ups (`updateMany where detailsCompletedAt is null`; a later call of that public server action changes the name and contact details but never the country or region). From then on only an admin changes it, on the company page ("Change region", audited `update_company_region`). The same first save sets `Business.timezone` for countries with one zone (Rwanda → Africa/Kigali, the EAC countries theirs, `COUNTRY_TIMEZONES`); elsewhere the browser sets it on the first dashboard visit. **Billing, checkout and the book-demo plan list always use the company region, never the IP** (`companyPlans(businessId)`).

## Soft region check (owner rule: prices for where people really are, without blocking real customers)

The sign-up country is self-declared, so a company could pick a cheaper country than where it is. `lib/region-check.ts noteRegionMismatch(businessId, source)` compares the request's IP country (the platform layer's `visitorCountry`: `cf-ipcountry` on Cloudflare, `x-nf-geo` on Netlify) with `Business.pricingRegion`:

- **When:** at sign-up (`ensureAccount` for email sign-ups, the first `/welcome` save for Google sign-ups; source `signup`), when a Mobile Money payment starts (`startMomoPayment`, plans and invoices; `momo`), and when a card checkout starts (`startCheckout`; `card`).
- **Mismatch** = the IP country is known (not missing, `XX` or Tor) and its region is **dearer**: its cheapest monthly plan, in USD (the card price of a local-currency plan), costs more than the company region's (RW $12 < EAC $25 < GLOBAL $49 with the seeds). Same region, a cheaper region, or a region without prices is never a mismatch.
- **What happens:** `Business.regionMismatch` (JSON: `country`, `ipRegion`, `companyRegion`, `source`, `firstSeenAt`, `seenAt`) and `regionMismatchAt` (set while open) are written. **Nothing is blocked**: the payment or sign-up goes on, and the check never throws (a failure is logged as `region.check`). The admin sees "Check region" on the company page (Demo and trial panel, next to the region selector) and a line on the Overview's attention list. **Change region** (audited `update_company_region`) moves the company and clears the flag; **Dismiss** (audited `dismiss_region_mismatch`, for a traveller or a VPN) closes it and keeps it as dismissed, so the same country is not raised again for that company (another dearer country is).
- Migration `20261014090000_region_mismatch` (two nullable columns and an index; safe in both deploy orders).

## Prices per region

`PlanRegionPrice` (`planKey`, `regionKey`, `currency`, `monthlyMinor`, `yearlyMinor`, `cardMonthlyUsdCents`, `cardYearlyUsdCents`, `paddleMonthlyPriceId`, `paddleYearlyPriceId`). Amounts are in the currency's smallest unit (RWF has none: 15000 = 15,000 RWF; USD in cents). Read through `lib/region-prices.ts`:

- `getRegionPlans(regionKey)` → `RegionalPlan[]` (a `PublicPlan` with the region's amounts and `currency`, plus `paymentMethods` and, for a local-currency plan, `card` = the USD card price). A plan is **offered in a region only when it has a price there**; hidden and retired plans are never offered.
- **GLOBAL is the plan builder.** Its amounts are the plan's own `monthlyPriceCents` / `yearlyPriceCents` and its Paddle ids are the plan's own (the existing price-change flow with 30 days' notice keeps working). A GLOBAL row only means "offered here". A plan with no regional price at all (one an admin just created) is offered in GLOBAL at its own price, so the plan builder works as before.
- Seeded by the migration: GLOBAL rows for every paid plan that existed (Standard $49/$490, Pro $99/$990, …); EAC Standard $25/$250, Pro $49/$490; RW Starter 15,000/150,000 RWF, Business 35,000/350,000 RWF (50,000/500,000 RWF since 14 October 2026, `docs/PLANS.md` "Video prices"). The two Rwanda plans (`STARTER`, `BUSINESS`: text 60/200, image 30/100, seats 1/3, features content, designs, calendar, gallery) are active and priced only in RW, so they appear nowhere else. Their plan-level USD price is the derived card price, which keeps the plan builder's own checks happy.
- Money is formatted with `formatMinor(minor, currency)` (`lib/region-format.ts`): "15,000 RWF", "$49", "$49.50". `components/billing/helpers.ts` wraps it as `formatPrice` / `formatPlanPrice`.
- **Mobile Money (R4, `docs/MOMO.md`) charges exactly these amounts.** `getMomoPrice(businessId, plan, interval)` (`lib/billing/momo-settings.ts`) reads the company region's `RegionalPlan` and `momoPriceOf()` takes its monthly or yearly amount; a region without `momo` in its payment methods, or a plan without a price there, has no Mobile Money price. The MoMo settings (Admin → Payments) hold only where clients pay. There is no second RWF price list anywhere.

**Card prices for RWF plans.** Two admin settings (**Admin → Settings**): USD→RWF rate (default 1,450; the same rate values Mobile Money revenue in USD for the roll-up, there is no other) and card margin % (default 12). `cardUsdCents(minor, currency, rate, margin)` = amount ÷ rate × (1 + margin), rounded **up** to whole dollars: 15,000 RWF → $11.59 → **$12**; 35,000 → $27.03 → **$28** (the storyboard says $27: the rounding rule from the brief gives $28; change the margin to 11% if $27 is wanted). Saving a regional price computes and stores the card price; "Update card prices" recomputes every local-currency row after a rate change (audited `update_card_prices`) and clears their Paddle ids.

**Paddle.** The regional card prices are created by `npm run paddle:setup -- --regions` (`docs/BILLING.md`, "Choosing how
to pay"); until a row has them, card shows as "Card payments coming soon" for that plan. Still TODO below: When the checkout exists, compare Paddle's billing country with the company's region at checkout (a GLOBAL-priced card paying from Rwanda, or the reverse) and decide what to do with a mismatch. The RW card prices and the EAC prices need their own Paddle prices (`PlanRegionPrice.paddle*PriceId`, or Paddle country `unit_price_overrides` on the plan's prices). Until they exist, `regionPriceIdFor()` returns null outside GLOBAL and checkout says "Card payments are not ready for your region yet. Pay by Mobile Money instead" (RW) or "Payments are not available right now" (EAC). Plan: a "Sync with Paddle" button on the Regions page that creates the prices (sandbox first) and, for a changed card price, moves subscribers through the existing `PlanPriceChange` flow. `BillingAdapter.checkoutConfig` already takes a `priceId` override.

## The demo-first trial (section 12)

No trial starts at sign-up, in any region. `SubscriptionStatus` has a new value, **`PENDING_DEMO`**; `ensureAccount` creates `{ plan: "TRIAL", status: "PENDING_DEMO", trialEndsAt: null }`. Existing companies are untouched.

1. **Choose a plan, book a demo** (`/book-demo`, owner or admin role). Step 1 lists the company region's plans (`choosePlan` → `Subscription.chosenPlan`). Step 2 lists free slots from the owner's availability (`bookDemo`). The dashboard redirects here while `PENDING_DEMO` and no plan is chosen (`components/app/context.ts`).
2. **Availability.** `AdminAvailability` rows (weekday, start and end minute, Africa/Kigali), seeded Monday–Friday 09:00–17:00; settings `demo.slotMinutes` (30), `demo.bufferMinutes` (15), `demo.blockedDates`, `demo.meetingLink` (the reusable Google Meet link), `demo.organizerEmail` (default hello@bupulse.com). `lib/demo/slots.ts` (pure, Intl-based zone maths) cuts slots: inside a window, not on a blocked date, at least 2 hours ahead (`MIN_LEAD_MINUTES`), over the next 14 days, and not within the buffer of a live booking. `bookDemo` re-checks the slot; two partial unique indexes back it up: `DemoBooking_live_slot_key` (`startsAt` where status = booked: two clients never take the same minute) and `DemoBooking_live_business_key` (`businessId` where booked: one live booking per company; a race on the first booking returns the one that won). The slot check and the write are not one transaction, so two clients booking neighbouring slots in the same instant can land inside the buffer: accepted, the owner sees both in Demos. **A reschedule moves the one booking in place** (same row, same calendar UID, `sequence` + 1), so calendar apps move the event instead of showing two; cancelling bumps the sequence too and sends `METHOD:CANCEL` for that UID. Once a booked slot's end has passed without the admin marking it done or a no-show, the client may book again (the same row moves). The actions are rate-limited per company (`DEMO_LIMITS` in `app/book-demo/actions.ts`: 10 plan choices, 5 bookings, 5 cancellations an hour).
3. **Emails and invites.** On booking, rescheduling and cancelling: one email to the client and one to every `ADMIN_EMAILS` address, with the time (Africa/Kigali), the meeting link, the chosen plan, a link to and an attachment of the `.ics` (`lib/demo/ics.ts`: RFC 5545 escaping, quoted `CN` parameters, lines folded at 75 octets). The **client's invite** names the organizer setting as `ORGANIZER` and only the client as attendee: the admin addresses never reach a client's calendar; the admins' copy adds them. The `.ics` route `/api/demo/ics/[token]` serves the client's copy; `DemoBooking.icsToken` is 32 random bytes (base64url, set by `newIcsToken()` in `bookDemo`), the route answers 404 for anything but a `booked` booking that ended less than a day ago, and is rate-limited per address (30 an hour). `sendEmail` gained optional `attachments` (Resend's base64 shape).
   **With Google Calendar connected** (Admin → Settings, `docs/GOOGLE_CALENDAR.md`): its busy times come out of the free slots, and each booking is also a Google event with a generated Meet link (Google sends its own invite; reschedule patches it, cancel deletes it). Without a connection, or when Google fails, the flow above runs alone. The emails and the lock screen also offer "Add to Google Calendar" (Google's template link) next to the `.ics`.
4. **Before the trial** the dashboard layout renders only `components/app/demo-lock.tsx`: "Your demo is on …", Join, Add to calendar, Reschedule (`/book-demo?step=time`), Cancel (both only up to 2 hours before, enforced in `lib/demo/bookings.ts`), the chosen plan, what happens next, and "Pay for <plan> by Mobile Money" where the region takes it (`docs/MOMO.md`). Server side, while `PENDING_DEMO`, the account is **read-only** (below): `lib/entitlements.ts` grants no features (gated pages say "Your demo comes first", actions and routes answer 403 `not_in_plan` with that message, the widget `unavailable`), `lib/usage.ts` throws `pending_demo` (402, the paywall dialog says "Your demo comes first"), and `/api/v1` keys see no `apiAccess`.
5. **Admin.** **Demos** page (upcoming / past / all, status filter): Mark done, No-show (with notes), **Start trial**. The same buttons and the region selector sit in the "Demo and trial" panel on the company page. Every action goes through `adminAction()` (allow-listed email + AAL2) and is audited (`update_demo`, `start_trial`, `update_company_region`). Jarvis read tools: `list_regions`, `list_region_prices`, `list_demos`.
6. **Start trial** (`lib/admin/demos.ts startTrial`): only from `PENDING_DEMO` with a chosen plan **that the company's region offers** (otherwise the admin is told which plans it offers, may pass `planKey` to pick one, or changes the region first); sets `status = TRIALING`, `plan = TRIAL`, `trialEndsAt = now + trial days`, clears the reminder stamps, marks the live booking done, emails the client, records `trial_started`. **Trial length** is the setting `trial.days` (default **3**, Admin → Settings). `change_plan` to TRIAL uses the same setting. The TRIAL plan's `trialDays` column stays editable but drives nothing any more (kept so older builds and the plan form keep working); `getTrialInfo()` still reads it for anything legacy.
7. **During the trial** the company has the **chosen plan's features with the TRIAL plan's limits** (`featurePlanKey()` in `lib/entitlements.ts`; usage reads limits from `Subscription.plan` = TRIAL). A chosen plan that was retired since falls back to the TRIAL plan's features. `extend_trial` works as before. The client pays from Billing (the company region's plans): by card through the existing Paddle flow, or by Mobile Money where the region takes it (`docs/MOMO.md`); confirming a Mobile Money payment makes the subscription `ACTIVE` on the paid plan. **Paying does not have to wait for the demo**: the lock screen offers "Pay for <plan> by Mobile Money" to the Owner (`components/app/demo-pay.tsx`), and a confirmed payment opens the dashboard.
8. **Trial end** (`lib/demo/trial-reminders.ts`, hourly cron `TRIAL_CRON` = `53 * * * *` → `/api/cron/trial-reminders`, `CRON_SECRET`, listed in `lib/admin/cron.ts` for the health page). For trials without a card on file (`providerSubscriptionId` null: MoMo clients and anyone who never added a card): a reminder when a day is left (day 2 of a 3-day trial) and one on the last day (8 hours before the end), each recorded on the subscription (`trialReminder1SentAt` / `trialReminder2SentAt`) before sending, so at most once; nothing is claimed while Resend is off, and a failed send is retried next run. When `trialEndsAt` passes, the subscription becomes `EXPIRED` (audited as `system:cron`), the client gets "Your trial has ended" (only when the trial ended within the last 48 hours: a legacy trial that ended long before the cron existed is closed quietly, audited with `emailed: false`), and the account is read-only (below): nothing is deleted, paying reopens it. `extend_trial` and `change_plan` to TRIAL clear `trialReminder1SentAt` / `trialReminder2SentAt`, so the reminders go out again for the new end. This cron only looks at `TRIALING` subscriptions; once a client has paid by Mobile Money (`MANUAL_MOMO`, `ACTIVE`) the renewal reminders and the grace period are the momo-renewals cron's (`docs/MOMO.md`), so no client ever gets both sets of emails. **Card clients (TODO, Paddle adapter):** at Start trial, open a Paddle checkout with a trial period so the card is on file and charged at the end unless cancelled; the webhooks then move the subscription to ACTIVE or CANCELED. Not implemented: no Paddle calls were added.

## Read-only accounts

`lib/entitlements.ts accountBlock()` mirrors the paywall in `lib/usage.ts`: an account is read-only while it waits for its demo (`PENDING_DEMO`), when its trial is over (`TRIALING` past `trialEndsAt`, or `EXPIRED`), when a payment failed (`PAST_DUE`), or when its plan ended (`CANCELED`). `companyEntitlements()` then returns the plan's features in `inPlan` / `usable` as before (**viewing stays**: pages render, the sidebar keeps its items, export and delete are not gated: "keep your data") with `block` set and `resolved: true`, and `featureStatus()` answers `not_in_plan` for every feature. So, consistently: actions and routes refuse with the reason (`FeatureRequiredError.block`: "Your free trial has ended. Choose a plan …", 403, never 503); the "Add to your plan" page says the same with a Billing button; Autopilot, the leads digest, the store sync, the webhook retry and the public widget skip or answer `unavailable`; `/api/v1` keys are refused; and the **publisher holds the company's posts**: `claimDuePosts` does not claim posts of companies whose subscription is not `ACTIVE` or `TRIALING`, and a claimed post whose account turns out blocked (a trial that ran out between cron runs) is released back to `SCHEDULED` with the reason on it (`lastError`), the attempt returned, never `FAILED`. When the company pays, held posts go out, the late ones first. Decided 12 October 2026.

## Copy

"Start free trial" became "Book a free demo" everywhere (header, mobile menu, hero, final CTA, plan cards, industries, about, blog, sign-up and welcome forms, confirmation email page, FAQ "How do I get started?", terms section 3). The trial banner and billing page keep "free trial" wording for companies that are on one. Copy stays industry-neutral.


**Webhook price ids.** `planForAnyPriceId` (`lib/region-prices.ts`) maps a Paddle price id to its plan: the plans' own ids and history first, then a region's `PlanRegionPrice.paddle*PriceId`. An id nobody knows is stored UNPROCESSED with an `unmapped` note (ErrorLog `billing.webhook.paddle.unmapped` and one email to the admins), and the route answers 200 so Paddle stops retrying. It is listed under **Admin -> Payments -> Card events not applied** with a **Reprocess** button (console, authenticator code, audited `reprocess_billing_event`) to run once the plan or region price is synced; a later Paddle replay of the same event is processed too. A database error during the lookup is not "unmapped": the route answers 500 and Paddle retries. A region price id is forgotten when its price is edited, so subscribers on an old regional price need a PlanPriceChange (no history is kept for region prices yet).
