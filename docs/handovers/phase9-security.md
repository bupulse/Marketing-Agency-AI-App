## New environment variables

- `API_KEY_PEPPER` (Worker secret, optional but recommended): `openssl rand -base64 32`, then `npx wrangler secret put API_KEY_PEPPER`. Without it the pepper is derived from `ENCRYPTION_KEY`. **Set it before the first key is created with the new code, and never change it** (nor `ENCRYPTION_KEY` while it is unset): changing it invalidates every REST and admin API key. Added to `scrubSecrets`'s list and `.env.example`.
- `DEMO_CAPTURE_PASSWORD` (local only, for `Demo/capture/*.mjs`).
- Turnstile keys are the existing `TURNSTILE_SITE_KEY` / `TURNSTILE_SECRET_KEY`; setting them now also protects sign-up. Add `bupulse.com` (and `localhost` for dev) to the Turnstile widget's hostnames.

## Migrations and deploy order

1. `20261012130000_internal_table_grants` (RLS + revokes, default privileges).
2. `20261012130100_storage_account_blocked` (function + Storage INSERT/UPDATE policies; skipped with a notice when there is no `storage` schema, like the earlier Storage migrations).

Order: back up, set `API_KEY_PEPPER` in the Worker (if used), `npx prisma migrate deploy`, then deploy the code. Both directions are safe for a short gap: the migrations only remove API grants nobody uses and tighten browser Storage writes; the old code's server uploads use the session and would be refused for read-only accounts only (which the app refuses anyway). The new code before the migrations works too (it only adds the service-key writes and limits). Existing API keys keep working through the legacy-hash fallback; no backfill. After deploy, move the GitHub deploy secrets to the `production` environment (docs/UPDATES.md) and reset the demo accounts' password.

Check after migrating (SQL editor): `select has_table_privilege('anon', '"ApiKey"', 'select')` → false; `select relrowsecurity from pg_class where relname in ('ApiKey','WebhookEndpoint','WebhookDelivery')` → all true.

## Not done / notes

- `checkEmail` still reveals a registered address within its limits (the owner wants known addresses sent to sign in). Removing it fully means dropping that UX; `signUp` already redirects known addresses.
- Sign-up limits count before Supabase's own; a shared NAT (school, office) shares the per-IP counters. The per-IP numbers are generous for that reason.
- The `+tag` normalisation is applied to every domain (not just Gmail): it only affects rate-limit counting, never the stored address.
- `submitAction` in the sign-up form builds a fresh `FormData` and drops `visitSession` (pre-existing; not changed here).
